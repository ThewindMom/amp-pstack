### Autopilot-full

Every PR owner needs an isolated checkout. Amp-native owners use explicit `launchTarget.kind: "parent-project-orb"`; CLI owners use their own snapshot worktrees and return reviewed patches. Follow `references/amp-adapter.md` for placement, transfer, and ownership. Only an explicitly authorized schedule supplies later wakes.

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until independent verification has proven the code that lands.** Orchestrate instead has a coordinator that lands work and workers that never merge.

A verification round is keyed by the exact head SHA. A verdict covers one patch and green CI covers one head. A full swarm runs once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result; every new head needs its own green CI.

1. **The operator's gates come first.** Items the operator names as theirs and PRs outside the authorized queue stop at merge-ready. A request to state the plan is not a go. Shared pushes, PR writes, merges, and auto-merge arms require explicit authorization for the agreed program and scope; a generic full-autonomy grant or a clean verdict alone does not authorize them.
2. **Spawn one owner per PR and preserve its work for a replacement.** Resolve the forge once. Default to `gh`; prefer `origin pr` when Origin can resolve the repository, otherwise record the fallback. Never require Graphite (`gt`). Spawn with `pstack_start_agent`. The owner builds, opens a ready PR early per `playbooks/opening-a-pr.md`, proves the real artifact, triages Bugbot per `../references/bugbot-triage.md`, babysits to green per `playbooks/babysit.md`, and merges only after steps 4 and 5 clear it.

   Code-ready follows the slop-strip (inspect the diff, then **unslop**) and **no-comments**. Rebase onto current trunk and report the code-ready head before self-proof, so self-proof, CI, babysit and independent verification can run in parallel on the intended base. Report every later head, and merge-ready when self-proof, CI and babysit finish. Fix rounds keep that base unless trunk conflicts, breaks CI, or a known concurrent change to the same files lands. Run the repo's required pre-review checks on the committed head before every push that needs a verifier; hooks alone are not proof.

   Assume the orb dies. Within about 15 minutes of starting, push and start `decisions.tsv` per **show-me-your-work**, in storage the root can retrieve. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Keep trails uncommitted and transfer them to the root at each report; copy their latest contents into the root's durable store, not only the child's filesystem. Whoever spawns a child records it in `children.tsv`, keyed by that child's thread ID, with state and expected runtime at least the longest past run of that kind. The root preserves these records too. Publish rebases only on the owner's own branch with `git push --force-with-lease` after an `ls-remote` check, pinned to the SHA last pushed or explicitly taken over. On an unexpected push, stop and report to the root. Never force-push a shared branch. That push still needs the operator's explicit authorization.
3. **Run independent owners in parallel off trunk, never stacked.** Only genuinely overlapping work serializes. Sequenced work is merge-then-branch; dependent stacks use Autopilot-stack.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and a wording-only change gets none. At each full swarm, fan out independent verifiers per **swarm**: gates, live load-bearing behavior on the actual surface through the available project verification skill or named browser/PTY driver, and two or more review lanes with distinct focuses that distrust the PR body. Each receipt names its exact SHA and method. Run the same load-bearing scenario on current trunk when possible; record missing features instead of inventing a comparison. Audit merge-ready receipts before giving a verdict. No clean verdict without the live lane.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, does not block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks; everything else goes in a follow-up. Send blocking findings to the owner in one fix-forward, with a repro receipt, and include them in the next verifier brief. Never push the owner's fix yourself. Each new head gets a fresh verdict except for results still valid under Shipping's patch-id rule.
5. **Merge only verified code tested on the trunk it lands on.** After the lanes start, merge prep rebases onto current trunk, reports the new head and waits for green CI. CI must pass on that head before the merge; apply Shipping's patch-id rule to its verdict.

   Right before merging, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Rebase and wait for CI when the code that would land was not tested: a conflict, a file both sides changed, or a change to which CI checks run. A lockfile both sides changed needs no rebase if a frozen install passes on the merge result and the packages the PR changes resolve as on its head; failure requires repair by rebase. If trunk changed a caller, called code, or dependency version, run the patch's checks on the merge result and merge only on a pass. Unrelated trunk movement alone needs no rebase. If trunk forces a third rebase past merge prep, hold and report to the root to sequence colliding work. Operator-named items wait for their click. With explicit merge authorization, the owner merges through the resolved forge and returns. A fresh owner, spawned with `pstack_start_agent`, picks up the next self-contained item with the prior report and transferred state.
6. **Run the root layer.** Anything that loosens a gate, including a raised budget or allowlist entry, needs verifier proof and then the root's fresh countersign. A disabled or soft-failed check comes out because it no longer guards every case. If the operator's authorization covers approvals, the owner's record points to the countersign for a lane to check. Never give or bypass approval enforced by the forge. Absorbing values already on trunk is drift, not a new loosening.

   On the operator's go for the requested ongoing run, arm an hourly Amp schedule (`set_schedule` with `RRULE:FREQ=HOURLY` and `run_mode: "existing"`) on the root. Clear it when no delegated work remains or on stop. Each tick re-reads this playbook from the loaded skill path or pinned plugin source, not from the target repo's trunk. Audit and repair drift by having the owner record unreported heads or children; missing records alone are not stalls. Probe the root's and all owners' children with Amp status and `children.tsv`, down to the leaf lanes. Judge progress by commits, pushes, PR/check deltas and trail rows, not summaries. Errors, inability to start turns, or no side effect past the recorded runtime mean stuck, as does no push or trail row by the first tick. An owner waiting on the root or operator is not stuck; answer it.

   Record each stuck child as stuck whether or not the stop works. Use `pstack_stop_agent` and confirm the prior owner is terminal. Replace it only after that child has stopped or reached a terminal state and its ownership claim is reconciled, and only if its work is still needed. Never two live owners for the same work. The root handles this if the owner cannot. A stall never proves or drops the work. Collect trails durably, run a retro and post-merge bot-comment sweep after merge batches, and keep auditing while any delegated work remains. Catch the operator up per **ketchup** only on a new tracked change; an unchanged tick stays quiet. Log every tick's row either way.
7. **Stand down at once on stop.** A hold reaches every owner as an immediate zero-writes order. Each reports its state and keeps its brief until released.

**Reply:** catch the operator up per **ketchup** with PR states and verdicts, merges, countersigns and why, open operator gates, parked follow-ups, and links to the PRs and collected trails.
