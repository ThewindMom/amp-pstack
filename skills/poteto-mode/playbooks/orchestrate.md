### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator thread: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with Amp's native tools. Spawn workers with `pstack_start_agent` following `references/amp-adapter.md`. Keep the program's state in the project's tracker (`notes.md`) and its agreed durable store; if none exists, use workspace-local notes rather than inventing a shared store. Watch each PR with PR and CI event subscriptions when available. Call no orchestration scripts, run no polling loops, and do not relay routine status between agents. Put dependencies in kickoffs; use native `send_thread_message` only for scoped follow-ups on the same work and required result delivery. Schedules need an explicit request. Shared tracker writes, pushes, PR creation, retargets, merges, and other shared writes still need explicit authorization.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call and within the user's authorization. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Use an orb for independent work from the remote project base unless the work needs this machine: local app or CLI verification, transcripts, a simulator, auth, or uncommitted state that exists only here. Select roles, models, effort, serving speed, and placement through `references/amp-adapter.md`, respecting user choices and executor limits. One writer per worktree or branch.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch. Nested delegation still requires the authority and tools granted to that child.
- **Keep built-state-dependent follow-ups with the worker that owns that state.** Amp has no assumed fork that copies a checkout, uncommitted changes, or a running process. A separate verifier needs an exact-state disposable copy or explicit file transfer through the adapter; a commit ID or message alone transfers nothing. Message a worker only for a follow-up on the same work, never to check on it. Use read-only thread status and PR activity for liveness.
- **Each PR gets a verifier that isn't its author,** on a different model family. The owner merges only on that verifier's pass at the current head and with explicit merge authorization.
- **Start with one unit.** Take it through kickoff, owner, verifier, and authorized merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. If merge is not authorized, stop the pilot at verified handoff and report that boundary rather than treating it as merged. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a control-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. A stall never releases ownership: use `pstack_stop_agent` and replace it only after Amp observes a terminal state and its ownership claim is reconciled. Never redo a live child's work. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible or unauthorized shared action, a product or preference call that no experiment settles, or a dead end that survived a replan. Within existing authorization, rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
