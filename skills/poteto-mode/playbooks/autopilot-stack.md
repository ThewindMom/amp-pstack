### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** The sibling of **Autopilot-full**.

Autopilot-full holds except for how verified work leaves. Each hourly Amp schedule tick re-reads both playbooks from the loaded skill path or pinned plugin source; this one wins where they differ. Owners never rebase onto another branch, trunk included, and never retarget, merge, close, or arm auto-merge. An owner of dependent work branches from its parent's branch rather than trunk. The root alone owns topology and the operator owns landing. Keep decision trails and `children.tsv` durable at the root per Autopilot-full step 2.

1. **Run the owner loop unchanged.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One Amp child per PR, spawned with `pstack_start_agent` following `references/amp-adapter.md`, owns its change end to end: build, first push, a ready PR opened before self-proof, self-proof (gates, CI, receipts), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip (inspect the diff, then **unslop**), **no-comments**, and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained. Shared pushes and PR writes still require the operator's explicit authorization. Once authorized, within about 15 minutes every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2, keyed by thread ID.
2. **Audit on a real schedule.** The root runs an audit tick every hour. On the operator's go, the root arms the hourly Amp schedule with a prompt that runs this tick, per Autopilot-full step 6. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from the loaded skill path Amp names after load, or from an explicitly pinned plugin source. Do not `git show origin/main:skills/...` in the user's target repo; that repo need not contain pstack. Audit the operation against it. Fix drift during that tick. Probe each owner with Amp thread status. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that passes its expected runtime without a side effect as stuck. Steer it to stop. A zero-writes steer is not proof it stopped. Confirm the prior owner has stopped or reached a terminal state. Reconcile its ownership claim before spawning a replacement. Never two live owners for the same PR. Probe stuck children and end the tick per Autopilot-full step 6.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with STACK-READY in place of merge-ready. A round is keyed by that exact head SHA. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it with `origin pr create --status open --base <parent-branch>` or `gh pr create --base <parent-branch>` according to the resolved forge. Retarget an existing PR with `origin pr edit <pr> --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never submit or register the chain through `gt`.
7. **Absorb drift at the root, then re-verify what moved.** Until landing starts, apply Autopilot-full step 5's merge-result test to each link and rebase bottom-up only where it requires one. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA, since each link's base is its parent. Anything no longer valid goes through step 4's full swarm or single-verifier policy before delivery. Re-run mergeability and CI after every rewritten push even when patch-id is unchanged. The countersign rule for any gate loosening is unchanged from Autopilot-full; absorbing landed values is drift, not a new loosening.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up in the resolved forge, every link carrying its verifier verdict in the PR body or a comment when the operator authorized that write. The operator reviews and lands it, with their own clicks or by arming merge-when-ready.

Until landing starts, apply Autopilot-full step 5's merge-result test to each link and rebase bottom-up only where needed. Apply Shipping's patch-id rule link by link. Each owner takes the root's push as its new base and lease. Once landing starts, nobody writes to the chain except Shipping's sanctioned post-merge move of the next PR. Any mid-landing fix goes through the root to the operator and waits for explicit authorization.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** catch the operator up per **ketchup**, with links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
